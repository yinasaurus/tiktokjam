Webinar Framing

The implementation should be presented as a conversational commerce system, not just a catalog search script. The four pillars map directly to repo work:

Pillar Repo Evidence Demo Message
Intent Routing & Hybrid Pipeline agent/routes/, RRF fusion, dense route, reranker. Buying favors hard constraints; browsing keeps broader candidate coverage.
Multi-Turn Scenario Evolution SessionState, asked/declined attributes, superseded slots. The agent accumulates preferences and handles abrupt intent override.
Dynamic Context Programming Active constraints are rebuilt every turn; question policy and deadline guard adapt runtime behavior. The workflow changes based on dialog history, candidate quality, and budget.
Product & Efficiency Metrics evaluator/local_evaluator.py, ablation runner, reranker benchmark. Coverage is retrieval recall; precision is MRR/top-rank movement; efficiency is fast convergence.

Model Choices

Hard rule for submission: no paid API calls and no hosted LLM dependency. The ranked output must run offline from the repo plus local participant-kit data.
Layer Use Why Where It Lives
Dense encoder Model2Vec static encoder, preferably potion-retrieval-32M-class. CPU-only, torch-free, small enough to commit if under 100 MiB, fast enough to build 50k embeddings locally. models/encoder/
Reranker LightGBM LGBMRanker with LambdaRank objective. Microsecond inference, small artifact, no API key, no transformer latency risk. models/ltr.txt
Fallback Current heuristic reranker. Keeps system shippable if trained LTR fails or has no measured uplift. agent/rerank.py
Do not use by default Cross-encoder, hosted LLM, or paid API reranking. Latency, offline scoring, packaging, cost, and secret-management risks outweigh likely gain for this competition. Only behind a benchmark gate, not the default path.

How To Train and Adopt the Ranker

  1. Create a deterministic train/holdout split: split the 200 public sessions into 160 train and 40 holdout by stable sample id hash. Keep the split script deterministic.
  2. Generate candidate pools: for each turn, run the current retrieval stack and keep top N_fuse candidates, including route scores, ranks, active constraints, category signals, title overlap, popularity, sparsity, and whether the candidate is the target.
  3. Train LightGBM LambdaRank: group candidates by query-turn/session. Label target as relevant, non-target as zero. Use NDCG/MRR-oriented validation.
  4. Save small artifact: write the booster to models/ltr.txt. This should be committed if it remains small, typically under 1 MiB.
  5. Wire inference: add an ltr path in agent/rerank.py that loads models/ltr.txt once, computes the same feature vector, and falls back to heuristic if the model is missing or malformed.
  6. Benchmark before enabling by default: measure p95 per-turn latency on all 200 sessions. Only set rerank_mode="ltr" or "cascade" if score improves without threatening the 500 ms turn budget.
The ranker target is narrow: promote rank-2 and rank-3 hits to rank 1 often enough to reach roughly 79% rank-1 share and about +0.039 TechnicalScore. Do not chase a heavy model unless LightGBM cannot move the public-set metric.
